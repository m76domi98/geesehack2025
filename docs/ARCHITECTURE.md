# Architecture

## The study loop
```
  Course (1..10 PDFs)
        │  one lesson episode per PDF, in upload order
        ▼
  Lesson episode ── script (2 hosts, chapters) ── audio (TTS)
        │
        ▼
  Quiz (each question tagged with a concept)
        │  every answer updates that concept's schedule
        ▼
  concept_schedule (Leitner box + due date)
        │  concepts due or recently missed
        ▼
  Review episode (short, only those concepts, fresh examples and questions) ──┐
        ▲                                                                     │
        └─────────────────────────────────────────────────────────────────────┘
```

Podcastify's job is to own **what you know over time**. Gemini writes and speaks; the backend decides what to study next.

## Components
- **Frontend (Vue 3 SPA):** four views (Today, New course, Course, Episode). It's stateless: every view loads from the API, so refreshing a page always works. In development, Vite proxies `/api` to Flask, so there's no CORS and no hardcoded URLs.
- **Backend (Flask):** routes in `app.py`, persistence in `db.py`, and all model calls in `gemini.py`.
- **Storage:** SQLite at `data/podcastify.db`. PDFs and WAV files go in `data/files/`, with paths generated by the server and never taken from user input.

## Gemini usage (`gemini.py`)
| Function | Model | Input → output |
|---|---|---|
| `write_lesson(pdf, prior_concepts, options)` | `gemini-3.8-flash` | PDF plus concepts from earlier lessons → `Lesson` JSON |
| `write_review(pdfs, concepts, options)` | `gemini-3.8-flash` | course PDFs plus target concepts → short `Lesson` JSON |
| `synthesize(script, voices)` | `gemini-3.8-flash-tts` | dialogue lines → WAV (24 kHz, mono, 16-bit) |
| `answer(pdfs, history, question)` | `gemini-3.8-flash` | course PDFs plus chat history → text |

All calls use the Interactions API (`client.interactions.create`). Structured output is checked with Pydantic (`Lesson.model_validate_json`).

`Lesson` schema:
```json
{
  "title": "…",
  "chapters": [{ "title": "…", "lines": [{ "speaker": "Host A", "text": "…" }] }],
  "concepts": [{ "name": "…", "summary": "…" }],
  "quiz": [{ "concept": "…", "question": "…", "choices": ["…"], "answer_index": 0, "explanation": "…" }]
}
```
The script, concepts and quiz come from **one** call, so they always match each other.

**Course continuity:** lesson *n*'s prompt includes the concept names and summaries from lessons 1..*n*-1, so the hosts can say "remember last time…" without resending earlier PDFs.

**Long audio:** if a script is too long for one TTS call, `synthesize` renders each chapter and joins the PCM frames with the stdlib `wave` module.

## Data model (`db.py`)
| Table | Key columns |
|---|---|
| `courses` | `id`, `title`, `options_json`, `created_at` |
| `documents` | `id`, `course_id`, `position`, `filename`, `path` |
| `episodes` | `id`, `course_id`, `kind` (`lesson` or `review`), `document_id?`, `position`, `title`, `script_json?`, `audio_path?`, `created_at` |
| `concepts` | `id`, `course_id`, `name`, `summary`, `episode_id`, with `UNIQUE(course_id, name)` |
| `questions` | `id`, `episode_id`, `concept_id`, `question`, `choices_json`, `answer_index`, `explanation` |
| `attempts` | `id`, `question_id`, `correct`, `answered_at` |
| `concept_schedule` | `concept_id` (PK), `box`, `due_at` |

Foreign keys are enforced (`PRAGMA foreign_keys = ON`).

## Spaced repetition
A Leitner system, implemented as the pure function `next_review(box, correct, now) -> (box, due_at)`:

| Box | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| Next review in | 1 day | 3 days | 7 days | 14 days | 30 days |

- **Correct:** move up one box (box 5 stays at 5).
- **Wrong:** go back to box 1.
- A concept is **due** when `due_at <= now`.
- `POST /api/courses/<id>/reviews` takes up to 5 concepts, in this order: due concepts, then concepts missed in their most recent attempt.

This is simple on purpose. If reviews feel badly timed, swap in SM-2 or FSRS behind the same function signature.

## Generation is lazy
Creating a course only stores PDFs and placeholder episodes. Scripts are generated when an episode is opened, and audio is rendered as a separate request. That keeps costs proportional to what you actually study, and it lets the UI show the script while the audio renders.

## Known limits
- Single user, no auth. It's meant to run locally. Going multi-user needs a `users` table, auth and per-user scoping on every query.
- Generation runs synchronously inside the request. That's fine locally; a hosted deployment would need a task queue.
- Transcript timing is estimated from character counts.
